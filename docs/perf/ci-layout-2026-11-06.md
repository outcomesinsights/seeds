# CI test jobs on titan: serial or concurrent

## Question

`just ci` runs its test jobs concurrently: the suite on the pinned Python, on
each matrix version, and the nix flake check. On 2026-11-05 one concurrent run
took 418–441 s for each job. A serial run took 140–198 s for each version.
Does running the jobs together cost that much?

## Setup

| Item    | Value                                                                                                       |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| Commit  | `454f4fc` (detached worktree)                                                                               |
| Host    | titan, 40 cores                                                                                             |
| Suite   | 1696 tests                                                                                                  |
| Pythons | 3.15.2 (pin, `just test`), 3.11.16, 3.12.3, 3.13.12 (`just test-python`); nix-check builds on nixpkgs' 3.14 |
| Tools   | uv 0.13.7, just 1.58.0, DuckDB CLI 1.5.6                                                                    |
| Script  | `claude_stuff/perf/ci-layout.zsh` (not committed), pueue task 765                                           |

The two layouts do the same work:

- **Serial:** `just checks`, `just test`, `just test-matrix`, `just nix-check`, one after another.
- **Concurrent:** `just ci`, which runs `checks`, then the other four together.

One concurrent warm-up run was discarded. Then three runs of each layout
alternated. Each run was one `titan-lock` perf iteration, timed inside the
lock. The lock reported every run CLEAN: no wrapped test suite ran during it.
The script started only after titan's mean CPU fell under 30% for 5 minutes.

## Results

| Run          | Wall time | Machine CPU (below) |
| ------------ | --------: | ------------------: |
| serial-1     |     204 s |                 18% |
| serial-2     |     195 s |                 20% |
| serial-3     |     197 s |                 33% |
| concurrent-1 |      55 s |                 23% |
| concurrent-2 |      59 s |                 43% |
| concurrent-3 |      61 s |                 39% |

The machine CPU includes the run itself. Five suites use about 5 of 40 cores,
which is about 12%.

Serial runs, per recipe: `checks` 1 s, `test` 45–47 s, `test-matrix`
143–149 s (about 48 s for each version), `nix-check` 4–6 s.

Concurrent runs, per job: each suite took 52–60 s, and `nix-check` took 5–6 s.

## Conclusion

The concurrent layout takes about 58 s and the serial layout about 199 s, so
it is 3.4 times faster. Running together makes each suite about 20% slower
(about 57 s instead of about 47 s). That is the full cost of concurrency here.

The 2026-11-05 numbers do not measure the layouts. titan was at 100% CPU from
about 06:00 to 08:56 that day, from load outside `titan-lock` (`xcloud-agent`,
a Spark JVM, root-owned ruby and `rake db:reset` test runs). The first attempt
(pueue task 763, log `claude_stuff/perf-ci-layout-20261105-085354.log`)
produced no timings: the titan DuckDB CLI segfaulted after a Home Manager
switch, and two DuckDB tests failed in every run.

## Decision

Keep `just ci` concurrent. GitHub CI runs each job on its own runner since
`454f4fc`, so this measurement applies to the push gate on titan only.
